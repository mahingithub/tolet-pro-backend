# TO-LET PRO — Deployment Guide (Phase Call-2)

Get the app live with HTTPS so mobile browsers can use camera/mic.

**Architecture after this phase:**

```
  Browser / Mobile
        │  HTTPS
        ▼
  Vercel  ──────────►  Render            ──────►  MongoDB Atlas
  (React/Vite,         (Node + Express +          (M0 free cluster,
   auto HTTPS)          Socket.IO, free tier)      Singapore)
                            │
                            └──► Cloudinary (images/video — already set up)
                            └──► Firebase Admin (phone-auth verify)
```

You will deploy in this order: **Atlas → Backend (Render) → Frontend (Vercel) → wire CORS back → Firebase domains.** There is a chicken-and-egg between the backend URL and frontend URL; the order below handles it.

---

## ⚠️ STEP 0 — Rotate the leaked secrets (do this first)

The local `.env` was shared in plaintext, so every secret in it must be treated as compromised. Rotate **before** pushing to GitHub (bots scrape new repos for keys within minutes).

| Secret | Where to rotate |
|---|---|
| **MongoDB password** | Atlas → **Database Access** → edit user `Asraf-Alom` → Edit Password → Autogenerate → Update User. Copy the new password into your new `MONGO_URI`. |
| **JWT_SECRET** | No manual step — `render.yaml` auto-generates a fresh one on Render. Locally, run `openssl rand -hex 32` and paste into your local `.env`. (All users get logged out — fine pre-launch.) |
| **Firebase service account** | Firebase Console → **Project Settings → Service accounts** → *Manage service account permissions* → Keys → delete the old key → **Add key → JSON** → download new one → re-encode (Step 3.4). |
| **Cloudinary API secret** | Cloudinary → **Settings → Security → Access Keys** → generate a new key, retire the old. |

The `VITE_FIREBASE_*` values are **not** secret (they ship in the public bundle by design) — no rotation needed. Just keep Firebase Security Rules tight.

## STEP 2 — MongoDB Atlas (free M0)

> Your existing URI already points at an Atlas cluster (`to-let-pro.kbuu4s7…`). If that's the cluster you want to keep, you can **skip creation** and just do 2.3–2.5 below (rotate password, network access, add a DB name). Otherwise create a fresh one:

**2.1 Create cluster** — [cloud.mongodb.com](https://cloud.mongodb.com) → Build a Database → **M0 (Free)** → Provider AWS → **Region: Singapore (ap-southeast-1)** (lowest latency to Bangladesh) → Create.

**2.2 Database user** — Security → **Database Access** → Add New User → username + autogenerated password → Built-in role **Read and write to any database** → Add.

**2.3 Network access** — Security → **Network Access** → Add IP Address → **Allow access from anywhere (`0.0.0.0/0`)**. Render's free tier has no static outbound IP, so this is required for now. (Restrict later when you move to a paid tier with static IPs.)

**2.4 Connection string** — Cluster → Connect → Drivers → copy the SRV string. It looks like:
```
mongodb+srv://<user>:<password>@to-let-pro.kbuu4s7.mongodb.net/?retryWrites=true&w=majority&appName=TO-LET-PRO
```
**Add a database name** before the `?` (your current URI is missing one, so Mongoose silently uses a DB called `test`):
```
mongodb+srv://<user>:<password>@to-let-pro.kbuu4s7.mongodb.net/toletpro?retryWrites=true&w=majority&appName=TO-LET-PRO
                                                                  ^^^^^^^^ add this
```
This final string is your `MONGO_URI`.

**2.5 Migrate local data (only if you have data in a local Mongo).** If you've been developing against this same Atlas cluster already, skip this.
```bash
# Dump from your local Mongo (adjust db name if different):
mongodump --uri="mongodb://localhost:27017/toletpro" --out=./dump
# Restore into Atlas:
mongorestore --uri="<your-new-atlas-MONGO_URI>" ./dump/toletpro
```
(Install tools if needed: `brew install mongodb-database-tools`.)

## STEP 3 — Backend → Render (via Blueprint)

**3.1 New Blueprint** — [dashboard.render.com](https://dashboard.render.com) → **New + → Blueprint** → connect GitHub → pick **`tolet-pro-backend`**. Render reads `render.yaml` and shows one web service named `tolet-pro-backend`.

**3.2 Fill the prompted env vars** — because the YAML marks secrets as `sync: false`, Render asks you for each. Paste:

| Key | Value |
|---|---|
| `MONGO_URI` | the Atlas string from Step 2.4 (with DB name + rotated password) |
| `FIREBASE_SERVICE_ACCOUNT_BASE64` | the base64 blob from Step 3.4 below |
| `CLOUDINARY_CLOUD_NAME` | `du5znfqgw` (or your value) |
| `CLOUDINARY_API_KEY` | your Cloudinary key |
| `CLOUDINARY_API_SECRET` | the **rotated** Cloudinary secret |
| `CORS_ORIGINS` | leave a placeholder for now, e.g. `http://localhost:5173` — you'll update it in Step 5 |

`NODE_ENV=production` and `JWT_SECRET` (auto-generated) are handled by the YAML — don't touch them. **Do not add a `PORT` variable** — Render injects it and your `config/env.js` reads it.

**3.3 Deploy** — click **Apply / Deploy Blueprint**. First build takes a few minutes.

**3.4 Encoding the Firebase service account** (run locally, before 3.2):
```bash
base64 -i path/to/new-service-account.json | tr -d '\n' > sa.txt
# open sa.txt, copy the entire single-line string, paste as the env value
```

**3.5 Verify** — when the deploy is **Live**, open:
```
https://tolet-pro-backend.onrender.com/healthz
```
You should see `{"ok":true,"db":"connected",...}`. If `db` says `disconnected`, your `MONGO_URI` or Atlas Network Access is wrong. **Copy this `onrender.com` URL — the frontend needs it.**

> 💤 **Cold-start note (matters for calls):** Render's free service sleeps after **15 minutes** of no traffic — and that includes idle WebSocket connections. The next request (or incoming call) takes ~30–60s to wake it. Step 7 mitigates this.

## STEP 4 — Frontend → Vercel

**4.1 Import** — [vercel.com/new](https://vercel.com/new) → import **`tolet-pro-frontend`**. Vercel auto-detects **Vite** (build `npm run build`, output `dist`) — leave those defaults. `vercel.json` handles SPA routing.

**4.2 Environment Variables** — expand *Environment Variables* and add all of these (values from your Firebase config; `VITE_API_BASE_URL` is the Render URL **+ `/api`**):

| Key | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://tolet-pro-backend.onrender.com/api` |
| `VITE_FIREBASE_API_KEY` | your key |
| `VITE_FIREBASE_AUTH_DOMAIN` | `to-let-pro-14e09.firebaseapp.com` |
| `VITE_FIREBASE_PROJECT_ID` | `to-let-pro-14e09` |
| `VITE_FIREBASE_STORAGE_BUCKET` | `to-let-pro-14e09.firebasestorage.app` |
| `VITE_FIREBASE_MESSAGING_SENDER_ID` | `100291826945` |
| `VITE_FIREBASE_APP_ID` | your app id |
| `VITE_GOOGLE_MAPS_API_KEY` | your Maps key (if used) |

**4.3 Deploy** → you get a URL like `https://tolet-pro.vercel.app`. **Copy it.**

> ⚠️ `VITE_*` vars are read at **build time**. If you change any later, you must **redeploy** for it to take effect.

## STEP 5 — Wire CORS back to the backend

Now that you have the Vercel URL, tell the backend to trust it.

Render → `tolet-pro-backend` → **Environment** → edit `CORS_ORIGINS`:
```
https://tolet-pro.vercel.app
```
(No trailing slash. Add `,http://localhost:5173` too if you still test locally.) Save → Render redeploys automatically. Both Express CORS and Socket.IO read this list, so this fixes API **and** socket connections in one shot.

---

## STEP 6 — Firebase + Maps domain allow-listing (easy to forget)

**6.1 Firebase authorized domains** — phone-auth/reCAPTCHA refuses unknown domains. Firebase Console → **Authentication → Settings → Authorized domains → Add domain** → `tolet-pro.vercel.app`. Without this, OTP login fails in production.

**6.2 Google Maps referrer** — Google Cloud Console → **APIs & Services → Credentials** → your Maps key → **Website restrictions** → add `https://tolet-pro.vercel.app/*`.

---

## STEP 7 — Keep the backend warm (recommended for a call app)

A sleeping backend won't ring an incoming call until it wakes (~30–60s). Ping `/healthz` every ~10 min to keep it warm:

- Go to **cron-job.org** (free) → create a job → URL `https://tolet-pro-backend.onrender.com/healthz` → interval **every 10 minutes**. (UptimeRobot works too.)

**Budget math:** the free tier gives **750 instance-hours/month**; a month is ~744 hours, so keeping **one** service awake 24/7 fits within the free allowance. Don't keep a second free service warm this way — two would exceed 750h and get suspended.

## Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `/healthz` shows `db: disconnected` | Wrong `MONGO_URI`, or Atlas Network Access doesn't include `0.0.0.0/0`. |
| CORS error in browser console | `CORS_ORIGINS` missing the exact Vercel URL, or has a trailing slash. Must match the origin exactly. |
| Socket won't connect | Same `CORS_ORIGINS` fix — Socket.IO uses the same list. Confirm backend redeployed after editing. |
| First load is slow / call doesn't ring | Free-tier cold start. Set up Step 7. |
| OTP / phone login fails in prod | Vercel domain not added to Firebase Authorized domains (Step 6.1). |
| Refreshing a deep route 404s | `vercel.json` not in the frontend repo root. |
| Build fails on Vercel | Ensure `package.json` build script is `vite build` (it is) and that you didn't accidentally `.gitignore` needed source. |
| Render build "cannot find module" | A dependency is in `devDependencies` but needed at runtime — move it to `dependencies`. (Not expected for your current setup.) |
